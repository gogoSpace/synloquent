# Laravel host integration

Synloquent exports explicitly registered Eloquent resources through an authenticated protocol endpoint. The package owns validation, scoped query compilation, mutation receipts, commit ordering, bounded snapshots and a durable effect outbox. The host owns policies, dataset membership, trusted attribute preparation and complete capture of every exported write.

## Install and register

For a local checkout, add a Composer path repository for `packages/laravel` and require `synloquent/laravel`. The package advertises its provider through Composer discovery. Its runtime dependencies and licenses are recorded in the dependency architecture decision. No package publication is required to run this repository.

```sh
composer install
php artisan vendor:publish --tag=synloquent-config
php artisan migrate
php artisan synloquent:doctor
```

The provider loads package migrations automatically. Publish migrations with `synloquent-migrations` only when the host intentionally takes ownership of their deployment. Do not install duplicate copies of both loaded and published migrations. New migrations extend installed tables without changing a released migration.

Register export classes, a trusted `ActorResolver`, optional `QueryScope` classes, typed `ServerCommand` classes and `EffectDestination` classes in `config/synloquent.php`. Keep `env()` reads inside configuration. Set the PostgreSQL connection `timezone` to `UTC`, configure a stable cursor signing secret and select the host authentication middleware. The doctor command verifies the live connection timezone because PostgreSQL and Eloquent must preserve the same datetime instant.

`examples/laravel` contains a runnable host with Country, ItemType, Series, Location, Salespoint, Item, Image, Tag, CollectionEntry, polymorphic Note and additional string identity fixtures. Its bearer tokens and default cursor secret are synthetic test values. Replace its resolver and authentication configuration in a real host.

```sh
composer --working-dir=examples/laravel install
php examples/laravel/artisan migrate
php examples/laravel/artisan synloquent:seed-example
php examples/laravel/artisan synloquent:doctor
php examples/laravel/artisan synloquent:generate --output=backend.generated.ts
php examples/laravel/artisan synloquent:generate --output=backend.generated.ts --check
```

The generated file exports `backendSchema`, `BackendModels`, `BackendCommands` and `BackendScopes`. Commit generated application bindings together with the corresponding server schema change when committing is authorized. The check command fails when a checked-in binding is stale.

## Exports, casts and authorization

An export declares readable fields, writable fields, operations and typed relation methods. Columns, standard casts, nullability, defaults, enums, keys and safe projected indexes are inferred from the actual model and database. Every exposed relation target must also be registered. An explicit morph map translates host classes into stable resource names. Unknown casts, missing relation return types and missing pivot field declarations fail closed.

`fillable` and `hidden` do not grant access. The resolver independently authenticates the actor and resolves account, tenant, device, epoch and authorization generation. The request session must match that trusted context. Each resource applies its current scope and policy to root queries, eager relations, relation predicates, joins, subqueries, unions, mutations and replayed receipts. Foreign key targets must exist in the actor's current authorized scope.

Use `prepare()` to assign trusted ownership values after validating writable attributes. For example, CollectionEntry assigns its actor and tenant from `ActorContext`. Its `localUnique()` declaration models uniqueness within that actor partition without exporting hidden actor identifiers or converting global database uniqueness into different semantics.

Declare custom cast wire types explicitly in `fields()`. Declare nonphysical PHP accessor fields in `materialized()`. Such fields export `materialized: true`, remain read-only and become available after canonical server materialization. Their offline generated value type includes `undefined` until that value arrives. The client does not execute PHP. Server predicates, ordering and aggregates over a nonphysical materialized field return `unsupported_query` rather than targeting an imaginary SQL column.

For writable standard `array`, `json` or `object` casts, add `Synloquent\Laravel\Concerns\PreservesJsonTypes` to the host model. Laravel normally compares those JSON values through associative decoding, which can treat `{}` and `[]` as the same dirty value. The trait compares canonical JSON for only those exact standard casts, preserving nested object and array types. It leaves custom casts, accessors and model events to the host. An equivalent object with different key order remains a no-op. Without the trait or an equivalent host comparator, the runtime rejects a proven JSON dirty mismatch with `unsupported_query`, and doctor names the affected field. HTTP JSON values retain their object and array identity during create, update, query, snapshot, download and receipt replay. Existing canonical primary keys remain immutable. A custom key is accepted during creation and an unchanged key may accompany an update.

Exact decimals travel as strings. Integers use safe JSON numbers or canonical integer strings, preserving values outside JavaScript safe integer bounds. Commands accept both declared integer representations and reject fractional or exponential strings. Dates use `YYYY-MM-DD`, datetimes use UTC ISO timestamps and model casts preserve actual host storage precision. The example exercises booleans, integers, decimal precision, float precision metadata, JSON, backed enums, a custom catalog code cast, UUIDs, ULIDs and a nonincrementing custom string primary key.

## Query and mutation contract

POST `/synloquent/v1/protocol` accepts the strict versioned envelope described in `docs/PROTOCOL.md`. Raw JSON is validated before converting objects into PHP arrays, so `{}` and `[]` retain distinct meanings. Unknown properties, malformed field values, excessive trees, excessive pages and excessive batches are rejected.

The portable AST supports bound comparison, grouping, negation, column comparison, relation predicates, declared eager includes, ordering, aggregate and grouped aggregate output, relation aggregates, scoped joins, correlated subqueries and unions. SQL identifiers come from registered field and relation allowlists. A string uses binary UTF-8 comparison. Ascending order places nulls first and descending order places nulls last.

Treat each physical field in `readable()` as a SQL read and inference grant for every row admitted by the resource query authorization and actor `scope()`. For example, omitting `quantity` in `project()` removes it from ordinary canonical records, but `max(quantity)`, grouping, scalar subqueries and predicates can still use it when it remains readable. `project()` controls serialized attributes, snapshot and pull visibility, and historical download reauthorization. It does not restrict SQL field use. Keep confidential fields out of the readable query export, and represent row policies in `scope()`. Use explicitly authorized commands for business output that cannot safely share the resource's query permissions.

Portable JSON containment tests scalar membership in a top-level array. Portable JSON paths allow dotted identifiers and numeric array indexes with scalar equality. SQL null, JSON null, booleans and numbers retain separate meanings. Object containment is an explicitly registered remote scope, `metadataContains`, in the example. Arbitrary SQL and unregistered scopes or commands are rejected.

Declared JSON scope and command arguments retain object versus array identity through HTTP decoding, Laravel validation and durable command replay. Laravel rules receive their normal associative validation data. The handler receives only validated keys with the original JSON types restored, including nested empty objects. Scopes apply to their authorized eager include, scalar subquery and union branches as well as the root query. Non-finite numeric values are rejected at the protocol boundary before writing domain rows or receipts.

Scalar and related aggregate output is read-only query data. It never becomes a writable canonical attribute. Decimal sum and average preserve exact string representation at the declared decimal scale. HAVING accepts bounded scalar predicates over declared group fields and the reserved `$aggregate` selector, including grouped boolean predicates. Group order, limit and offset apply after HAVING. Unsafe integer sums and averages retain exact strings, including grouped results. Ordinary query records and revisions are read in one PostgreSQL read-only repeatable-read transaction, with revisions fetched only for returned identities. The query action rejects an existing outer transaction.

Every push operation carries an immutable `operationId`, stable `localIdentity`, dependencies and a declared action. Existing records use a canonical revision. Missing or stale revisions conflict and retain a canonical proposal separately from the client's pending edit. Accepted operation identities cannot be reused with different payloads. Alias resolution stays within the actor, device and epoch partition, and tagged references must match their declared foreign resource and name the accepted creation operation in `dependsOn`. The alias ledger stores that operation identity. Legacy aliases without a recorded creation identity cannot authorize a tagged reference and must use their known canonical identity.

An `atomicGroup` commits all of its bounded operations together. A failed group rolls back domain rows, revisions, aliases, publications and effects before persisting its rejection receipts. Keep the entire group within the configured batch bound. Splitting a large group into independent requests changes its atomicity.

`eventMode` defaults to `instance`, preserving Eloquent casts, timestamps and instance events. Explicit `bulk` mode validates policies and casts on model state, then writes through scoped builders without instance observer callbacks. Both modes capture canonical rows and durable receipts in the same transaction. A pivot operation validates target scope and pivot fields. Destructive `sync` additionally requires a complete set and a matching directed relation revision. Hidden memberships remain attached. Related targets and existing membership reads are bounded. Nonprimary owner and related keys resolve to canonical identities in relation-set output.

## Capture and commit ordering

All exported instance writes, bulk updates and deletes, pivots, database cascades and command writes must obey the host capture contract. Declare `capture_contract: gateway` only after routing every such write through `WriteGateway`. The doctor validates that declaration, it cannot audit arbitrary host writers.

```php
$gateway->transaction($actor, function (WriteContext $context) use ($actor): void {
    $item = Item::query()->lockForUpdate()->findOrFail(1);
    Gate::forUser($actor->user)->authorize('update', $item);
    $item->title = 'Updated stamp';
    if (! $context->save($item)) {
        return;
    }
    $item->tags()->syncWithoutDetaching([1 => ['position' => 2]]);
    $context->captureRelation($item, 'tags');
});
```

The gateway owns the outer transaction and acquires the tenant stream lock before domain reads or locks. Do not wrap it in an existing transaction. Domain changes, revision advances, immutable publications, aliases, mutation receipts and outbox records use one database connection. Publication sequence advances under that lock in actual commit order. Rolled-back transactions publish nothing.

Use `WriteContext::save($model, $options = []): bool`, `delete($model): ?bool` and `forceDelete($model): ?bool` for host instance writes. They use the existing context and transaction. Save stages referential updates, calls the actual Eloquent `save`, refreshes the owner, completes dependent capture and captures the owner. Physical delete stages deletion dependencies before the native instance method, completes dependent capture and publishes a tombstone. Soft delete refreshes and captures an upsert, including any staged referential timestamp effects. Native owner events and casts run normally. Database cascades do not synthesize descendant events. A successful call already captures its owner, so do not add a second owner capture.

The helper uses a savepoint on the same connection so a cancelled observer returns the native `false` or `null` result without retaining that call's staged revisions, descriptors or effects. A thrown exception restores that call's context checkpoint and rolls back its database work before propagating. Earlier work in the callback remains available if the host catches the exception. An uncaught callback exception rolls back the outer transaction. As with ordinary Eloquent transactions, rollback does not rewind model objects or external observer effects. Reload an existing model, or recreate a new model, before retrying after an exception. Use the durable effect outbox for external effects.

Read existing models inside the gateway callback after the stream lock is held. Apply host validation and explicit policies there, as shown above. The context orchestration is a capture API, not a replacement for host authorization, and it does not restrict trusted host writes to client-exported operations. A declared owner stream is checked before and after native events. Automatic dependencies still require trusted resolvers on every involved export. Primary identities remain stable after creation, while a staged writable nonprimary natural key may change. Observer writes to unrelated rows, raw SQL, bulk writes and pivot changes retain their explicit capture contract.

The gateway closes the context in a `finally` block immediately after its callback. Every mutating context method rejects use after that boundary, including from an after-commit observer or inside a later transaction. Reading its captured changes and effects remains possible for publication. The advanced `capture`, `captureMany`, `captureRelation`, `invalidateAuthorization` and explicit staging APIs remain available within the active callback.

The protocol mutation action stages actual PostgreSQL `ON UPDATE CASCADE` dependencies before changing an existing model. A changed writable nonprimary owner key can update child foreign keys and recursive composite foreign keys in the database. Every changed registered dependent receives one new revision and an upsert descriptor in the same publication, including rows hidden from the current actor. Pull nominates these identities and applies its current row and field authorization. A stale child revision then conflicts. The original owner keeps its Eloquent events. Database cascades do not synthesize child instance events. Explicit bulk mutations retain their builder event behavior.

The update capture bound includes the owner and all unique affected models, and caps the pending traversal frontier. It uses `max_delta_records`, currently 1000. Exceeding that bound rolls back the complete mutation. A cascade that would rename a dependent primary identity is rejected. A referenced key changed only by an unstaged host observer is also rejected after the database operation, with the entire transaction rolled back. A populated unregistered dependency table or an update action other than cascade requires explicit host capture and is rejected by this automatic path. This includes bare pivot tables without a registered model. Keep such owner keys immutable through the protocol or implement and verify a dedicated host command with complete capture.

Automatic referential capture requires a trusted `captureStream(Model $model): ?string` declaration on the owner and each registered dependent export. Its default is `null`, which means the host has not established a stream. Resolve the stream from trusted row partition data, matching `ActorContext::stream()`. The example explicitly hashes its actual `tenant_id`. The generic package does not assume a tenant column or derive membership from an actor's SQL scope. An actor-private row in the same tenant stream is captured even when its scope excludes it. A row in a different stream, an unknown resolver or a partition change detected after the database write rejects the whole automatic mutation. Cross-stream transfers and shared rows require a dedicated, verified host orchestration of every affected stream. One old-stream capture cannot establish a complete transfer. Keep partition ownership and referential dependencies within the verified stream, preferably with database constraints. This resolver is a trusted host declaration, and doctor cannot infer its business meaning. Ordinary writes without automatic referential dependencies retain their existing authoring contract.

The update traversal groups old parent key tuples by model and changed columns, then loads each bounded recursive frontier together. It preserves ordered composite tuples rather than creating independent key combinations. Changed dependents reload together, and their revisions advance through parameterized PostgreSQL `UPSERT RETURNING` in chunks of 1000 under the stream lock. Batched capture deduplicates identities, preserves exact revision strings and gathers incoming pivot owners once per declared relation and model group. Revision, projection and dependency changes still share one atomic publication.

For a host command or another gateway write that changes a natural owner key, prefer `context->save($model)` after assigning the intended values. Advanced orchestration can still use `UpdateCapture::stage($model, $context)`, native save and refresh, `complete($plan, $model, $context)` and owner capture in that order. This authoring contract covers PostgreSQL referential effects. Arbitrary related writes performed by host observers still require the host's explicit gateway capture. Do not bypass model events to make an unstaged observer key change pass. After an atomic group rollback, new conflict receipts are rebuilt from the scoped committed model and revision, so they cannot promote canonical values from the aborted group.

For a physical deletion with exported foreign-key dependents, prefer `context->delete($model)` or `context->forceDelete($model)`. In advanced explicit orchestration, call `DeletionCapture::stage($model, $context)` before deleting and `complete($affected, $context)` afterwards within the gateway. Then capture the deleted parent with `capture($model, 'delete', true)`. The protocol mutation action already follows this order. It reads actual PostgreSQL foreign-key metadata, recursively locks and stages registered cascade dependents, captures nullified rows with new revisions and rejects dependency sets above the atomic bound. The same trusted stream guard verifies staged owner and descendants before SQL deletion, current nullified rows afterwards, and incoming pivot owners before advancing their directed relation revisions. Unknown and foreign streams roll back. A direct parent-only delete capture cannot establish complete dependency capture. Deletion completion reloads staged identities together by model in chunks of 1000. It verifies each current nullified row before advancing any revisions, then captures missing rows as deletion descriptors with `dependenciesCaptured: true` and current rows as upserts through the same bulk revision store. Each staging invocation builds its own incoming FK descriptor index from the current registry. A visited parent examines only declarations referencing its table, while preserving registry order, ordered composite key comparisons, stream checks and the existing traversal bound. Every relevant query gets a new Eloquent builder from the declaration model. The index is not shared between invocations, so a newly registered deeper dependency is discovered on the next call. Existing foreign-key metadata caching remains unchanged. Database cascades preserve the owner instance events without synthesizing child instance events. Soft delete publishes a canonical upsert containing `deleted_at`, and snapshots retain such records so portable `withTrashed` and `onlyTrashed` remain meaningful. Capture pivot membership through `captureRelation()`, including previous affected identities after detach. Incoming pivot dependencies are discovered across the whole export registry, including one-way relation exports. After detach, supply previous affected target identities so inverse relation revisions and journal descriptors also advance. When a host permission change affects dataset membership, call `invalidateAuthorization()` under the same stream lock and advance the trusted authorization generation when its policy semantics change. External writers currently require this gateway contract. An observer alone cannot capture builder updates, raw SQL or independent writers.

## Pull, snapshots and retention

Normal pull uses a normalized historical membership index. An unchanged cursor reads stream and checkpoint metadata without reading domain rows or parsing the membership catalog. A bounded captured interval reauthorizes its changed identities, affected incoming relations and scoped pivot targets, then compares only their indexed historical membership. The whole interval is coalesced into one final-state batch at the committed high-water. It preserves transaction groups, emits `delete` for physical deletion and `remove` for loss of access, and clears affected directed relation sets explicitly.

This path requires every export to declare `selfContainedProjection(): true`. The declaration is a host contract, not an automatic proof. Scope and projected fields must depend on that row and trusted actor authorization generation. Resource and field policy changes must advance that generation. Every writer must capture the affected rows, foreign-key dependents and pivot memberships before commit. Cross-row ACL rules, time-dependent scopes, external state and undeclared dependencies must retain the default `false` declaration or emit explicit global invalidation. A changed authorization generation forces reauthorization even at the same stream sequence. Do not use the declaration to cache an unproven permission result.

Unknown dependencies and authorization invalidation take a conservative materialization path capped at 5,000 record and relation-set members. Larger catalogs require a fresh snapshot with `cursor_expired`. Incremental intervals are capped at 1,000 transactions, 1,000 captured identities and 8 MiB of recorded changes. Scoped relation targets are bounded before allocation. Normal defaults also cap snapshots at 200,000 records and 64 MiB, requests at 1 MiB, push batches at 100 operations, query pages at 1,000 rows and pull response content at 8 MiB. An incomplete journal, expired membership history or oversized response fails closed.

The PostgreSQL benchmark compares 7,000 and 117,000 canonical records. Unchanged pull uses five SQL operations, and bounded single-row and 100-row changes use twenty. Development samples measured roughly 2–5 ms unchanged, 9–12 ms for one edit and 27 ms for 100 edits, with no additional allocated-memory growth relative to the post-snapshot baseline. Actual writer barriers preserve the subsequent anchored tail. These are synthetic observations, not deployment latency promises.

Public HTTP and CLI snapshots now encode, validate and initialize historical membership in bounded batches through an owned spool. The earlier full catalog implementation measured about 519 MiB and scanned the whole catalog on every poll. The current HTTP development fixture contains 117,115 records, 51,128 directed relation sets and 28.64 MB of canonical bytes. Cold creation measured 10.62 seconds, 30.38 MB logical peak and 53.82 MB allocated peak under the default 128 MiB PHP limit. A warm content reuse measured 8.91 seconds and skips blob readback and insertion. Authenticated download measured about 4.63 seconds. Whole-lifecycle hooks run after response send, and an independent sampler measures the owned worker RSS separately. RSS includes native driver buffers and allocator retention, so it exceeds logical PHP live memory. Final exact-candidate reports supersede these development observations. Snapshot construction remains O(dataset) and holds the stream lock. It is an initial or recovery operation, while normal polling scales with captured changes.

The structured performance artifact includes both sizes, actual row counts, resident memory, peak growth, SQL profiles, stream lock duration and PostgreSQL `EXPLAIN ANALYZE` plans for Item, pivot and historical membership lookups. Planner statistics are refreshed outside measured operations after bulk fixture insertion. Historical membership uses per-key indexed version lookup, and the PHP 8.4 PostgreSQL driver uses transactional bounded COPY chunks for fresh membership initialization. Other supported PDO variants use bounded inserts. A killed or rolled-back initialization leaves neither state nor membership rows committed.

Snapshot construction acquires the stream lock before reading the domain. It atomically persists canonical content, subscription membership, base cursor and an actor/device/epoch download grant. Its digest is SHA-256 of canonical `{records, relationSets}` bytes. Metadata is validated independently. Snapshot generation includes the actual opaque cursor, content digest, scope, dataset generation and actor partition, so unchanged content with different metadata has a different immutable URL.

The normal snapshot response includes inline records and `downloadUrl`. GET `/synloquent/v1/snapshots/{generation}/{hash}` returns the same immutable snapshot. It checks content and metadata integrity, current resource scopes and current field access in batches. Revoked historical access denies the whole download because filtering its content would change the published digest.

Cursors bind dataset, schema, authorization generation, account/device partition and stream position. The durable retention floor survives an empty publication journal. Snapshot grants pin their publication tail. Retire an unused grant through an explicit host retention policy before moving the floor beyond its base cursor. Never prune a ready snapshot's tail while a client may still install it.

## Typed commands and external effects

Scopes declare model, arguments, validation and authorization. Commands declare argument and result field types, validation, authorization, an immutable operation identity and safe replay behavior. The example exposes `increaseQuantity` and `inspectItemLocked`, whose `update` and `shared` modes use actual PostgreSQL `FOR UPDATE` and `FOR SHARE` within the gateway. Results and replayed results are validated against the declared shape.

Commands append external intentions with `WriteContext::effect()` rather than executing an external action inside the domain transaction. Run `synloquent:deliver-effects --limit=100` after commit. Concurrent workers lock committed outbox rows with `FOR UPDATE SKIP LOCKED` and acknowledge successful delivery durably.

An `idempotent` destination must persist the supplied idempotency key in the downstream system. A worker can die after external delivery and before acknowledgement, so that destination sees the same key on retry. A destination declared `at_least_once` may visibly repeat the effect. The fixture includes both a downstream idempotent implementation and a deliberate duplicate-producing control. Queue status alone does not establish exactly-once external delivery.

## Reproduce verification

```sh
cd packages/laravel
vendor/bin/phpunit
vendor/bin/phpstan analyse --memory-limit=1G --no-progress
vendor/bin/pint --test
```

Tests use real PostgreSQL commits, independent PHP processes, actual HTTP servers, explicit barriers and actual backend lock state. HTTP stream recovery tests inject catalog, membership and content-persistence failures, verify transactional rollback and spool cleanup, and verify lock release through a subsequent real HTTP write. They cover mutation rollback, commit order, death before commit, lost response replay, death after external success, snapshot lock order, immutable anchored tails, strict HTTP validation, current authorization and download corruption. They do not wrap those recovery tests in an outer test transaction.

Run `vendor/bin/phpunit --filter '(UpdateCascadeTest|DeletionStreamTest)'` for referential update and deletion controls. To emit new task-owned update fan-out measurements, set `SYNLOQUENT_UPDATE_FANOUT_PROFILE=1` and a distinct `SYNLOQUENT_UPDATE_FANOUT_LABEL`, then run `vendor/bin/phpunit --filter update_descendants_profile`. Preserve the existing baseline files when comparing a new candidate. The tests verify recursive composite keys, exact unsafe integer keys and revisions, bulk event semantics, atomic rollback, actor-private same-stream capture, current pull authorization and rejection of unknown or foreign stream dependencies.

Set `SYNLOQUENT_TEST_DATABASE` for an isolated task database and `SYNLOQUENT_TEST_AUTOLOAD` for a separate installed consumer. Create `synloquent_performance_laravel` in the task cluster, then run the large benchmark with `php packages/laravel/tests/Fixtures/performance.php`. Its reset guard rejects database names outside `synloquent_performance_`.

Current limitations remain explicit. The production database witness is PostgreSQL 18.3. Initial snapshot stream lock duration still requires a host workload decision. The internal array-returning snapshot action materializes its result and is intended for callers that explicitly need an in-memory document. Public HTTP, download and CLI paths use bounded batch processing. Default unknown-dependency exports use a bounded fallback and resnapshot rather than the normal incremental path. The matching bundled RN transport requests authenticated immutable `parts-v1` snapshots. Whole-document snapshot and download paths remain available. Snapshot transfer currently has no compressed wire format. Arbitrary PHP execution, arbitrary SQL, unnamed commands, external writers without gateway capture and nonphysical server SQL predicates are outside the supported runtime contract.
